New features that are still being tried out start off, with a switch under
`experiments` in `runner.json` (the user guide, "Experiments", says how to turn one
on). These are the ones there are now.

## What each one does

<!-- list:start -->
- **Keep the Mac awake** (`keepAwake`, since 6 Nov 2026). While any thread is working, and for three minutes after, your Mac won't go to sleep on its own, so a long turn, or one you started from your phone, isn't cut off halfway. The screen still dims and locks as usual. It stops below 15% battery when you're not plugged in, and closing the lid on battery still puts the Mac to sleep.
- **Review by another lab** (`labReview`, since 6 Nov 2026). When a turn that changed code (five lines or more, not counting docs) finishes with nothing for you to do, Threadbear starts a review thread in the same folder on your other provider: Codex reviews a Claude thread's change, and Claude a Codex one's. It's told to try to break the change and not to edit anything. It runs with the same permissions as the thread it reviews: a Full access thread's review has full access, and one in Ask before edits or Auto asks or checks the same way, so a change made from text you don't trust can't get its tests run with no card. The thread says who is reviewing, and hibernates until the review finishes. Then it wakes with the findings, fixes what holds up, and says in its reply what was found and what it did. The review thread is archived when it's done, so it stays out of your inbox; the link in the note opens it. A thread gets at most two reviews between your messages. With no login of another provider, a fresh session of the same one reviews, and the note says it isn't another lab. A folder a pool is kept for (Accounts, pools and Usage, above) is only ever reviewed on that pool's logins.
- **Diagrams and pages in replies** (`richBlocks`, since 6 Nov 2026). Tells agents that Threadbear draws ```` ```mermaid ```` and ```` ```html ```` blocks (Reading a reply, above), so they use one when a picture explains better than words. The apps draw those blocks either way; this is only whether agents are told.
- **Schedule checks** (`scheduleChecks`, since 6 Nov 2026). A schedule can have a check: a shell command that runs first, in its folder, each time it's due. If the check prints nothing, that run is skipped and no agent starts, so a schedule that looks for new Sentry issues every five minutes only uses a login when there's something to look at. What it prints is added to the message. If the check itself fails, the run goes ahead with the error, so you hear about it. A check has a minute to finish, or up to five if its schedule says so, for one that reads something slow like Slack. What a check prints is kept until a run carrying it has been sent, so a runner restart in between doesn't lose it. Ask a thread to "only run when there's something new" and it writes the check. Run now skips it. It's bound to what it runs: if a script it reaches changes, it doesn't run until the same check is passed to the schedule again, and the thread is told once.
- **Loose ends on the done card** (`looseEnds`, since 7 Nov 2026). When a thread finishes with nothing for you to do, Threadbear checks what's still open before you archive it: commits on its worktree's branch that aren't on main, files in its worktree that aren't committed, threads it started that are still working or waiting for you, and check-ins it booked. If there's nothing, the done card shows just Done, so Archive is safe without asking the agent first. If there is, it lists them under "Still open" (a thread opens from its line; Land is the chip above the message box). A check-in alone shows under "Coming back", as the thread comes back by itself when it runs. It checks again when you open the thread, after an action like Land, and when a thread it started finishes. The phone's done card doesn't show it yet.
- **Reply buttons** (`replyButtons`, since 7 Nov 2026). An agent can put buttons partway through its reply, beside the line they're about, so you can set jobs off as you read without typing: one starts a new thread with a brief the agent wrote ("Fill in the form"), another sends a message to a thread that's already going. Hover over a button to see the brief and where it runs. Nothing happens until you press it, and it only runs once: after that it turns green and opens the thread it started. It works the same on your phone and the website. A thread without Full access can't make a button that does more than it could itself, and that's checked again when you press it.
- **Standing instructions** (`standingInstructions`, since 7 Nov 2026). An Instructions box in Settings > General, for what every agent should always keep in mind: who you are, how you like things written, what you build with. Every new session gets it, on every login, Claude and Codex alike, and a chat that's already going hears a change before your next message, with a line in the thread saying so. It saves as you type; empty is none. A login's own `CLAUDE.md` or `AGENTS.md` still applies, and is the place for what's particular to that login or provider: this is for what goes for all of them, without keeping several files in step. Only what you save in Settings counts. If anything else changes the file (an agent, say), no agent is given it, Threadbear warns you, and the box shows what the file holds so you can keep it or clear it. Agents can't change this for you, so ask one to draft them and paste it in yourself. On Full access an agent that goes after the runner's own key could still get past this, as it could with anything on your Mac.
- **Move to another machine** (`moveToRunner`, since 8 Nov 2026). A thread moves to another of your machines whole: the same thread, with its whole conversation, its pictures and Highlights, and the git work in its own worktree (commits and uncommitted changes alike). It waits for the turn it's on to end, and messages sent meanwhile go with it. Its next message carries on in the same Claude session on the other machine. If anything goes wrong before it lands, it stays where it was and says why. So far it's started from the main Mac's runner (`threads.move`); the Mac app's **Move to** menu and `move_thread` with a `runner` come next. It needs Threadbear's backend, and the experiment on in both machines' runners.
- **Card reviewer** (`cardReviewer`, since 9 Nov 2026). In a thread on Auto, when something would stop for your OK (an edit to a file Threadbear runs as code, a message to a thread with more access, anything else that puts up an approval card), a reviewer looks at it first: Opus, with no tools, shown the card in full and what the thread was asked to do. If it fits the task and can't do real harm, it goes ahead, and the transcript says "Allowed by the reviewer" with its reason. If the reviewer has doubts, or can't run (no pool, a private folder, a card too long to read whole), the card comes to you as before, after a note with its reason. The reviewer is told that everything it reads is data, and that text trying to tell it what to answer is a reason to hand the card to you. Cards that hand out access lasting past the one action (switching a thread to more access, starting a thread with more, a schedule, moving a thread or changing its logins) always come to you. Codex threads' own tool cards come to you too, as they name the files a change touches but not the change. Ask before edits, Full access and plans are left alone: Ask means a person looks.
- **Voice mode** (`voiceMode`, since 7 Nov 2026). A waveform button beside Send in the Mac app, to talk with a thread out loud and have its replies read out ("Talking with a thread" in the guide). It lives in the app, which reads the switch when it connects to the runner, so turning it on or off takes effect when the app next connects (quit and reopen it). While it's off there's no button and no Voice tab in Settings, nothing downloads and macOS never asks for the microphone. With it on, Settings > Voice > Use with Notes (off by default) adds a waveform button to Notes for talking into a note ("Notes" in the guide).
- **Connectors setup** (`connectorsSetup`, since 8 Nov 2026). Puts the Connectors panel (the plug on the left-hand rail) in reach before there's a gateway, with a Set up button. Set up starts a thread that installs plugbear on this Mac, listening only on 127.0.0.1, and wires each of your logins to it. Once it's running, Add a service lists services it can add (Notion, Slack, Linear, Sentry, Cloudflare, DeepWiki) and takes any other MCP server by its https address. Each Add starts a short thread that adds it to plugbear and hands you its Connect button. Slack needs a Slack app of your own, and that thread walks you through it. Sign-ins and tokens stay in plugbear, never in Threadbear.
- **Outside agents** (`outsideAgents`, since 8 Nov 2026). Lets an agent that runs in the cloud, such as Grok Bot, use Threadbear as an MCP server. In the Connectors panel, Connect Grok Bot makes a key for it and shows the server address (your backend's `/mcp`). A read-only key can list and read threads it started, or every live thread if you tick that. A key that can write can also start threads, which always run in Ask mode so every tool asks you first, and message the threads it started while they stay in Ask mode. It never sees approvals, secrets, schedules or archived threads. Messages from it say who sent them, so threads don't take them as yours. Revoke ends a key on its next call, and turning this off ends every key.
